# CoinFT 固件逆向工程 - 项目背景

## 1. 项目概述

### 1.1 目标

对 CoinFT V2 电容式力传感器固件进行完整逆向工程，目标是：

1. **理解固件工作原理**：12 路电容传感器如何采样、处理并输出数据
2. **恢复可执行模型**：创建能够逐字节复现硬件行为的软件模拟器
3. **支持固件重建**：提供足够的技术细节，使得从零重写功能等价的固件成为可能
4. **验证行为等价性**：在真实硬件上验证恢复的模型与原始固件一致

### 1.2 为什么需要逆向

**原始固件不可用**：
- 无源代码
- 无调试符号
- 无技术文档
- 只有从硬件读取的 HEX 文件

**业务需求**：
- 需要修改采样率和数据处理逻辑
- 需要添加新的通信命令
- 需要理解传感器标定机制
- 需要优化功耗和性能

### 1.3 硬件基本信息

| 项目 | 规格 |
|---|---|
| **主芯片** | Infineon PSoC 4 (CY8C4149AZI-S593) |
| **架构** | ARM Cortex-M0+, 48 MHz |
| **Flash** | 128 KB（实际固件约 18 KB） |
| **SRAM** | 16 KB |
| **传感器类型** | 12 路电容式力传感器（CapSense CSD） |
| **通信接口** | UART（115200 baud, 8N1） |
| **存储** | Em_EEPROM（用于设备 ID 和校准参数） |

## 2. 技术挑战

### 2.1 无符号表

从硬件读取的 HEX 文件不包含：
- 函数名
- 变量名
- 类型信息
- 注释

**解决方案**：通过调用图分析、寄存器访问模式和数据流追踪推断语义

### 2.2 CapSense 中间件

固件使用 Infineon CapSense 库，但：
- 库的精确版本未知
- 配置参数嵌入 Flash，格式未公开
- 需要逆向 MSC（Multi-Sense Converter）硬件的 14 个操作寄存器

**解决方案**：
1. SWD 实时采集 MSC 寄存器快照
2. 对比多个扫描周期，识别配置模式
3. 查阅 PSoC 4 数据手册验证位域定义

### 2.3 实时验证

固件以 ~201 Hz 运行，调试时需要：
- 不影响时序的采样方法（SWD 后台读取）
- 同步 UART 输出与 SRAM 状态
- 处理跨扫描周期的撕裂读

**解决方案**：
- 开发 `sync_capture_v46.py` 工具，协调 SWD 和 UART 采集
- 使用时间窗口匹配算法关联 SRAM 快照与 UART 帧
- 82249 帧无筛选往返测试验证模型正确性

### 2.4 多轮迭代

初始假设经常被后续实验推翻：
- **v47**：误认为 field2/field3 恒零 → **v54** 确认确实恒零（清除污染后）
- **v51**：误认为 history[1] 恒零 → **v53** 推翻，发现是条件写入
- **v43**：未确定 SAR 用途 → **v53** 确认 `chan_en=0`，未使用

**解决方案**：建立 `fact_registry_v48.json`，追踪每个结论的证据链和修正历史

| 维度 | 含义 | 达标标准 |
|---|---|---|
| **D1 控制流** | 所有函数已识别 | 151/151，无未知函数 |

| **D3 数据结构** | 运行时数据结构字节精确 | record/history/frame/EEPROM |

| **D6 不可恢复项** | 不可恢复部分明确列出 | 变量名/注释/原始配置/raw 生成 |

#### 静态分析
- **Ghidra 11.1.2**：反汇编、反编译、调用图分析
- **自定义脚本**：
  - `classify_functions_v50.py`：函数角色分类
  - `validate_facts_v48.py`：事实登记表完整性检查

#### 动态分析
- **OpenOCD + KitProg3**：SWD 调试，实时读取 SRAM/寄存器
- **UART 抓包**：FT232 转 USB，捕获 26 字节帧
- **同步采集**：`sync_capture_v46.py` 协调 SWD 和 UART

#### 验证工具
- **模拟器**：`coinft_sim_v52.c`（600 行 C11）
- **往返测试**：`sim_roundtrip_v52.c`（82249 帧验证）
- **一致性套件**：`test_v52_conformance.c`（回放硬件观察）

### 4.3 证据链管理

每个结论都记录在 `fact_registry_v48.json`，包含：
- **claim**：具体断言
- **evidence**：支持证据（SWD 读取、UART 抓包、反汇编）
- **first_recovered**：首次确认的版本
- **significance**：对整体理解的意义

三种状态：
- **established**（已确认）：28 项
- **open**（待解决）：6 项（其中 4 项不阻塞交付）
- **superseded**（已推翻）：11 项（记录错误假设）

## 5. 关键技术突破

### 5.1 MSC 配置恢复（v18-v42）

**挑战**：MSC 有 14 个扫描 slot，每个配置 10+ 个寄存器，Flash 中的参数格式未知。

**突破**：
1. SWD 实时读取 MSC 寄存器（`0x40290000 + offset`）
2. 对比 14 个 slot 的配置差异，识别通道/电极映射
3. 追踪 Flash `0x238` 附近的配置段读取
4. 验证：用恢复的配置重新运行固件，输出一致

**成果**：14/14 配置帧逐字段匹配

### 5.2 tare 无条件语义（v51）

**挑战**：固件接受 4 字节 tare 命令（`t` + index + 2 字节参数），但 index=0xFF 时仍执行 tare。

**突破**：
1. 发送 `t 0xFF 0x00 0x00` → UART 继续发送数据（未报错）
2. SWD 读取：**所有 13 条 baseline 都被更新为当前 raw**
3. 反汇编确认：tare 逻辑在参数校验**之后**，即使拒绝写入扫描参数，baseline 仍会更新

**成果**：揭示了一个关键的"非原子性"设计 —— tare 与参数写入是两个独立步骤

### 5.3 行为等价验证（v52）

**挑战**：如何证明模拟器"足够正确"？

**突破**：
1. **不验证 raw 生成**（那是物理过程，无法从代码恢复）
2. **只验证数字路径**：给定相同 raw，能否复现 UART 输出
3. **无筛选测试**：直接走真实字节流，每帧解码→喂入模拟器→重新编码→逐字节比对
4. 82249/82249 帧通过，0 次重同步滑动

**成果**：这是现有证据能支撑的最强等价性声明

### 5.4 MLP 通道映射（v53）

**挑战**：12 路 raw → 6D wrench（Fx/Fy/Fz/Mx/My/Mz）的映射在 host 侧 MLP，固件不知道。

**突破**：
1. 提取 `mlp_local_jacobian_at_tare.csv`（在零力点的局部梯度）
2. 分析每个通道对 6 个力分量的敏感度
3. 发现：
   - Fz（法向力）主导 11/12 通道（敏感度 0.008~0.016）
   - Fx/Fy（剪切力）低 10 倍（0.001~0.004）
   - c11 是"万能通道"，对所有 6 个自由度都有贡献

**成果**：理解了传感器的物理特性（法向敏感，剪切不敏感）

## 7. 适用场景

### 7.1 完全重建固件

**目标**：从零编写功能等价的新固件

**适用于**：
- 需要修改核心逻辑（采样率、滤波算法）
- 需要适配不同硬件（其他 PSoC 型号）
- 需要添加新功能（无线通信、多传感器融合）

**所需资源**：
- 本交付包的伪代码和寄存器映射
- ModusToolbox 3.0+ 或 PSoC Creator 4.4+
- ARM GCC 工具链
- PSoC 4 数据手册

### 7.2 理解现有固件

**目标**：在不修改固件的情况下，理解其行为

**适用于**：
- 开发上层应用（数据处理、标定工具）
- 诊断硬件故障（判断是传感器还是固件问题）
- 优化 MLP 模型（理解 12 路 raw 的物理意义）

**所需资源**：
- 本交付包的架构文档
- MLP Jacobian 映射表
- UART 协议规范

### 7.3 扩展功能

**目标**：在现有固件基础上添加新命令

**适用于**：
- 添加校准命令（保存/恢复 baseline）
- 添加诊断命令（读取 history 数组）
- 修改 UART 帧格式（增加 CRC 校验）

**所需资源**：
- 命令协议规范
- Em_EEPROM 读写逻辑
- 阻塞语义说明
