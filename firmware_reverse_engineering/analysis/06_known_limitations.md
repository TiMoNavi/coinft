# CoinFT 固件逆向工程 - 已知限制与不可恢复项

## 1. 概述

本文档列出逆向工程过程中**无法恢复**或**未完全确定**的内容，并说明其对固件重建的影响。

**关键结论**：
- ✅ 所有不可恢复项都不影响固件重建
- ✅ 行为等价性已通过 82249/82249 帧验证
- ⚠️ 2 个实现细节未完全闭合，但有绕过方案

---

## 2. 不可恢复项（D6）

以下内容**原理上无法从二进制固件恢复**，已在交付文档中明确说明。

### 2.1 符号信息

| 项目 | 原因 | 替代方案 | 影响 |
|---|---|---|---|
| **函数原始名称** | 符号表不存在 | 用地址命名（FUN_XXXXXXXX） | 无，代码可读性略降 |
| **变量原始名称** | 符号表不存在 | 用语义命名（record, baseline） | 无，推断名称已足够清晰 |
| **类型定义** | 符号表不存在 | 从访问模式推断（uint16_t, struct） | 无，类型已确认 |
| **宏定义** | 预处理阶段消失 | 用常量替代（MSC_BASE = 0x40290000） | 无 |

**结论**：符号信息丢失不影响行为等价性，伪代码中的命名已足够支持重建。

### 2.2 注释与文档

| 项目 | 原因 | 替代方案 | 影响 |
|---|---|---|---|
| **代码注释** | 不在二进制中 | 本交付包的文档 | 无 |
| **设计文档** | 外部资料 | 架构文档（02_） | 无 |
| **变更历史** | 版本控制信息 | 逆向过程记录（restoration_progress） | 无 |

**结论**：本交付包提供了完整的逆向文档，可替代原始注释。

### 2.3 编译器细节

| 项目 | 原因 | 替代方案 | 影响 |
|---|---|---|---|
| **编译器版本** | 未知 | 推测为 ARM GCC 6.x-10.x | 无，重建时用最新版 |
| **优化级别** | 未知 | 推测为 -O2 或 -Os | 无，重建时选择合适优化 |
| **链接脚本** | 未知 | ModusToolbox 默认脚本 | 无，只要内存布局兼容 |

**结论**：编译器细节不影响重建，只要行为等价即可。

### 2.4 原始配置意图

| 项目 | 原因 | 替代方案 | 影响 |
|---|---|---|---|
| **MSC 参数选择依据** | 需要设计文档 | 直接复制恢复的寄存器值 | 无 |
| **14 个 slot 的映射逻辑** | 需要源码 | 按观察到的模式配置 | 无 |
| **field2/field3 设计用途** | 需要源码或设计师访谈 | 写为 0（恒零已验证） | 无 |

**结论**：不理解原始意图，但可以精确复现行为。

### 2.5 物理层（raw 生成）

| 项目 | 原因 | 替代方案 | 影响 |
|---|---|---|---|
| **电极几何形状** | 需要 PCB 设计文件 | 视为黑盒，只关注 raw 输出 | **无** |
| **电容-力转换模型** | 依赖材料和结构 | 由 MLP 在 host 侧完成 | **无** |
| **噪声特性** | 依赖硬件环境 | 固件不处理滤波 | **无** |

**结论**：固件只负责采集 raw，不负责物理建模。重建固件时**无需理解电容传感原理**。

### 2.6 CapSense 中间件版本

| 项目 | 原因 | 替代方案 | 影响 |
|---|---|---|---|
| **CapSense 库版本** | 未标识 | 用最新版或手动管理寄存器 | 可能需要调参 |
| **库的配置参数** | 嵌入 Flash，格式未公开 | v18/v42 恢复的寄存器序列 | **关键：必须精确复制** |

**结论**：重建时可选择：
- **方案 A**：手动管理 MSC 寄存器（推荐，完全控制）
- **方案 B**：用 CapSense Tuner 近似配置（需调参验证）

## 3. 未完全闭合的实现细节

以下 2 项在 v54 仍标记为 "open"，但**不阻塞固件重建**。

### 3.1 limit_word 与 cdac_sel_re 的精确关系

**现状**：
- 已确认 `cdac_sel_re` 写入 MSC `SW_SEL_CSW[bit10..15]`（v42）
- 已确认 `limit_word` 存在于 Flash 配置段（v18）
- **未确认**：`limit_word` 如何影响 `cdac_sel_re` 或其他 MSC 参数

**推测**：
- `limit_word` 可能是 compensation IDAC 的上限
- 或是 `cdac_sel_re` 作用的电容充电时长限制

**影响评估**：
| 场景 | 是否受影响 |
|---|---|
| 直接复制 v18/v42 的寄存器值 | ❌ 不受影响（值已确认） |
| 修改 MSC 参数（如灵敏度） | ⚠️ 可能受影响（需实验验证） |
| 适配不同 PSoC 型号 | ⚠️ 可能受影响 |
| 完全重建当前固件 | ❌ 不受影响 |

**绕过方案**：
1. **不修改 MSC 配置**：直接复制 v18/v42 恢复的寄存器写入序列 → 100% 安全
2. **用 CapSense Tuner**：让官方工具生成配置 → 自动处理 `limit_word` 关系
3. **实验测试**：修改后实测 raw 输出，迭代调整

**建议**：
- 初次重建：用方案 1（直接复制）
- 优化后：用方案 2（CapSense Tuner）

### 3.2 slot/LAST 的精确时序

**现状**：
- 已确认扫描顺序：slot 0 → 1 → ... → 13 → LAST
- 已确认 SCAN_COMPLETE IRQ 在 slot 13 后触发
- 已确认 UART 帧率约 201 Hz
- **未确认**：
  - 每个 slot 的精确扫描时长（微秒级）
  - CONFIG_REQ 中断的延迟
  - SCAN_COMPLETE 到 UART 发送的延迟

**推测**：
- slot 0→1 切换约 350 µs（逻辑分析仪粗测）
- 完整扫描周期约 5 ms（从 201 Hz 反推）

**影响评估**：
| 场景 | 是否受影响 |
|---|---|
| UART 输出一致性 | ❌ 不受影响（只要保证顺序） |
| 采样率约 201 Hz | ⚠️ 微小差异可接受（200-202 Hz） |
| 实时性要求（< 10 ms） | ❌ 不受影响 |
| 与其他传感器同步 | ⚠️ 可能需要精确测量 |

**绕过方案**：
1. **保证功能正确**：只要扫描顺序和 IRQ 逻辑正确，微秒级时序差异不影响 UART 输出
2. **测量实际时序**：用逻辑分析仪测量重建固件的实际时序
3. **调整扫描参数**：通过 `sense_width` / `comp_divider` 微调周期

**建议**：
- 初次重建：忽略精确时序，验证 UART 输出一致性
- 优化后：用逻辑分析仪测量并调整

## 4. 已解决但语义未完全理解的项

以下项目已通过实验**确认行为**，但**语义不完全清楚**。

### 4.1 field2 / field3（已确认恒零）

**现状**：
- v47：111644 次采样全零
- v54：额外验证，清除污染后全零
- 反汇编：存在写入路径，但条件恒为假

**推测**：
- 预留字段（为未来功能保留）
- 只在特定模式下使用（如触摸检测模式）
- 调试标志（发布版被优化掉）

**影响**：
- ❌ 无影响（写为 0 即可）

**重建建议**：
```c
record[ch].field2 = 0;  // 预留，恒为零
record[ch].field3 = 0;  // 预留，恒为零
```

### 4.2 history[1] 的完整语义

**现状**：
- v53：污染测试证明固件使用 history[1]
- v53：10/12 通道在 5 秒内未写入，2/12 通道部分字节被改写
- **未确认**：写入条件是什么

**推测**：
- 与 `negdiffcount` 相关的累加器
- 可能用于检测"持续负偏差"（电极故障、环境漂移）
- 写入条件可能与通道索引或 raw-baseline 关系有关

**影响**：
- ⚠️ 微小影响（不影响 UART 输出，但可能影响长期稳定性）

**重建建议**：
```c
// 初步实现：简单模仿 history[0/2/3] 的逻辑
if (diff < 0 && record[ch].negdiffcount < 255) {
    history[ch][1] += abs(diff);  // 累加负差值
}

// 或：直接忽略（UART 输出不依赖它）
history[ch][1] = 0;
```

### 4.3 SAR 的预留用途

**现状**：
- v53：SAR_CTRL.enabled=True，但 chan_en=0x00000
- 所有 17 个通道未使能
- 固件配置了 SAR 寄存器但从不执行转换

**推测**：
- 预留给温度补偿（通道 16 通常是内部温度传感器）
- 预留给电源监控（VDD/2 分压）
- 未完成的功能

**影响**：
- ❌ 无影响（当前固件不使用）

**重建建议**：
```c
// 方案 1：完全不初始化 SAR
// (最简单，安全)

// 方案 2：初始化但不使能通道
sar_init();  // 设置 SAR_CTRL.enabled
*(volatile uint32_t*)SAR_SAMPLE_CTRL = 0x00000000;  // chan_en=0

// 方案 3：启用温度监控（扩展功能）
sar_init();
*(volatile uint32_t*)SAR_SAMPLE_CTRL = 0x00010000;  // 使能通道 16
```

### 4.4 empty_stub 的 8 个函数

**现状**：
- v54：8 个函数反汇编为空函数体（只有 `return;`）
- 调用点：初始化链、条件调用、清理钩子、除零处理、孤立

**推测**：
- 预留钩子（模块化设计）
- 调试残留（`#ifdef DEBUG` 块被清空）
- 编译器优化（内联后留下的空壳）

**影响**：
- ❌ 无影响（可安全忽略）

**重建建议**：
```c
// 直接不实现这些函数
// 或实现为空函数（如果调用图需要）
void reserved_hook_1(void) { }
void reserved_hook_2(void) { }
```

## 5. 工具链限制

### 5.1 SWD 采样的撕裂读

**问题**：
- SWD 读取 33 字节 record 需要 ~10 ms
- 在 201 Hz 扫描周期中（5 ms），87.8% 的读取会跨越扫描边界
- 导致读到的 record 是"撕裂"状态（部分旧值 + 部分新值）

**影响**：
- ⚠️ SWD 验证不可靠（测试 A 失败率 87.8%）
- ✅ UART 验证可靠（测试 B 成功率 100%）

**解决方案**：
- 用 UART 往返测试替代 SWD + UART 同步匹配
- 或在固件中添加"双缓冲"机制（写入备份 record，SWD 读取备份）

### 5.2 Ghidra 反编译的局限

**问题**：
- 循环展开识别不完美（某些循环被误识别为顺序代码）
- 间接跳转表（switch/case）需要手动标注
- 浮点运算可能被误识为整数（本项目无浮点）

**影响**：
- ⚠️ 伪代码可读性降低
- ✅ 行为等价性不受影响（通过验证确认）

**解决方案**：
- 手动重构伪代码（v51 已完成）
- 用模拟器验证行为（v52 已通过）

### 5.3 Flash 配置段定位困难

**问题**：
- Flash 0x238 附近是代码段，不是配置段
- 配置段可能动态生成或分散存储
- v54 未完全定位 `limit_word` 在 Flash 中的位置

**影响**：
- ⚠️ 无法直接修改 Flash 来测试 `limit_word` 效果
- ✅ 不影响重建（直接复制寄存器值）

**解决方案**：
- 方案 1：不定位 Flash，只复制 MSC 寄存器写入序列
- 方案 2：用 CapSense Tuner 生成配置（自动处理 Flash 布局）

## 6. 硬件相关限制

### 6.1 电极布局未知

**问题**：
- 12 个电极在 PCB 上的物理位置未确认
- 通道编号（c1..c12）与 UART 帧顺序的对应关系假设为顺序映射
- 实际可能存在重排（如 c1 → UART[5]）

**影响**：
- ⚠️ MLP 通道映射可能需要重新标定
- ✅ 不影响固件重建（UART 输出顺序保持一致即可）

**验证方法**：
- 在已知位置施加力，记录 12 路 raw 响应
- 用 MLP Jacobian 反推电极位置

### 6.2 外部元件参数

**问题**：
- Cmod（调制电容）容值未确认（推测 2.2 nF）
- Csh（shield 电容）是否存在未知
- 电极材料和镀层未知

**影响**：
- ⚠️ 更换 PCB 或元件后，MSC 配置可能需要重新调参
- ✅ 不影响当前硬件的固件重建

**建议**：
- 用原始 PCB 和元件
- 或用 CapSense Tuner 重新生成配置

### 6.3 温度特性

**问题**：
- 温度对电容的影响未量化
- SAR 温度监控未启用
- 无温度补偿算法

**影响**：
- ⚠️ 在极端温度下（-40°C / +85°C），raw 可能漂移
- ✅ 室温下（20-30°C）影响很小

**建议**：
- 如需温度补偿，启用 SAR 通道 16 并在 host 侧实现补偿算法

## 7. 应用层限制

### 7.1 MLP 模型依赖

**问题**：
- 固件只输出 12 路 raw
- raw → Fx/Fy/Fz/Mx/My/Mz 的映射在 host 侧 MLP
- 更换传感器或 PCB 后，MLP 需要重新训练

**影响**：
- ⚠️ 固件可用，但力输出需要重新标定

**建议**：
- 保留原始 MLP 权重（`coinft_XXXXXXXX_MLP.onnx`）
- 或用新的标定数据集重新训练

### 7.2 Teensy 桥接依赖

**问题**：
- CoinFT 固件只负责单板 12 路
- 双板组合（左右板 → 58 字节 USB 包）在 Teensy 中完成
- Teensy 固件未在本项目范围内逆向

**影响**：
- ⚠️ 更换 Teensy 或修改桥接逻辑需要额外工作

**建议**：
- 保留 Teensy 原始固件
- 或用 USB-UART 桥接芯片替代 Teensy

## 10. 风险评估

### 10.1 重建固件的风险

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| UART 输出不一致 | 低 | 高 | 往返测试验证 |
| MSC 配置错误 | 中 | 高 | 用 v18/v42 值或 CapSense Tuner |
| 命令协议错误 | 低 | 中 | 6 个命令逐一测试 |
| Flash 操作失败 | 低 | 低 | Em_EEPROM API 验证 |
| 长期稳定性问题 | 中 | 中 | 24 小时压力测试 |

### 10.2 未知风险

**可能存在但未发现的问题**：
- 隐藏的故障处理逻辑（如看门狗复位）
- 低概率的边界条件（如 raw=0 或 65535）
- 多板同时运行的干扰

**建议**：
- 在实际应用中逐步验证
- 保留原始固件作为备份
- 建立故障日志机制

## 11. 结论

### 11.1 限制汇总

**不可恢复项**：6 项（全部不影响重建）  
**未完全闭合**：2 项（有绕过方案）  
**已确认但语义不清**：4 项（不影响行为等价）

### 11.2 对重建的影响

✅ **完全重建当前固件**：无阻塞，82249/82249 帧验证通过  
⚠️ **修改 MSC 参数**：需要实验验证（`limit_word` 关系未知）  
⚠️ **适配不同硬件**：需要重新标定（电极布局、Cmod 容值）  
⚠️ **扩展功能**：需要理解相关模块（如启用 SAR）

### 11.3 置信度声明

**高置信度**（> 95%）：
- 主循环状态机
- UART 编码
- record 结构
- tare 机制
- 命令协议

**中等置信度**（80-95%）：
- MSC 配置参数关系
- history 数组完整语义

**低置信度**（< 80%）：
- field2/field3 的原始设计意图
- SAR 的预留用途
- 极端工况下的行为

### 11.4 最终建议

**初次重建固件**：
1. 直接复制 v18/v42 的 MSC 寄存器序列
2. 实现主循环状态机和 6 个命令
3. 通过往返测试验证（目标：100% 一致）

**优化和扩展**：
1. 用 CapSense Tuner 重新生成配置
2. 启用 SAR 温度监控
3. 添加 CRC 校验和自动 tare

**生产部署前**：
1. 24 小时稳定性测试
2. 极端温度测试（如有条件）
3. 多板同时运行测试
4. 与原始固件对比测试（双盲）
